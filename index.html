Manual QA Workflow

One ticket in. A tested verdict out, with evidence. It works with any web system: it sets up the test environment, designs tests from the code change, runs them in a real browser, checks what happened behind the UI, and files a report.

Built by Kirill Molkov, Senior Automation QA Engineer

How it works

  1. One ticket in

    You give the agent a ticket key. That is the whole input.

  2. It prepares

    It builds the test environment, switches the feature on, seeds test data and gets test users ready.

  3. It designs the tests from the code change

    Happy paths first, then what can go wrong: wrong input, edge cases, another user's access, a neighbouring feature, another time zone, bulk load.

  4. It runs the tests in a browser

    It clicks, types and saves like a person, checks the result and saves a screenshot as proof.

  5. It reports

    It writes REPORT.md as it goes: the verdict and exact build, proof for every result, findings with steps, cause and a suggested fix, and open questions for the product owner. Then it files a test execution in the test management system, with every case, its steps, its result and its screenshot.

Beyond the UI

The agent does not stop at what the screen shows.

Full DevTools access

Console, network, page elements, storage and performance.

It checks what was really saved

After each browser step, a database query confirms what the system stored.

It reads the logs

It reads the logging systems the environment is connected to and ties each error to the step that caused it.

It checks roles and access

The same screen opens as each role, and every action is checked against what that role is allowed to do.

It tests the integrations

It follows one action through every connected service and checks what each one receives and sends back.

It runs load tests

It ramps traffic up step by step and finds the point where response times break the agreed limit.
